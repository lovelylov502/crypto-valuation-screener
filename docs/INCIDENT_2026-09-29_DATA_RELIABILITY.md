## 원인과 이전 보수의 누락

1. **직접 계기: 시세 공급 접근 차단.** 운영·GitHub 수집·로컬 단일 요청 모두 CoinGecko 403을 확인했다. 응답 본문은 CloudFront의 `Request blocked`다. 403은 접근 차단이며 호출량 제한을 뜻하는 429와 다르다. 구체적인 차단 정책·IP·계정 원인은 확인하지 못했다. 무조건 재시도하거나 유료 API로 바꾸면 해결된다고 단정하지 않는다. [CoinGecko 오류 정의](https://docs.coingecko.com/docs/errors-and-rate-limits)
2. **실패 자료의 공개를 허용함.** `lib/sources.ts:112`의 조회는 실패를 상태로 남기고 빈 시세 결과를 반환한다. `lib/collectionQuality.ts:17`은 성공한 응답에서 값을 버렸는지는 검사하지만 `status=error` 자체를 공개 차단 조건으로 삼지 않는다. `lib/screener.ts:37`의 조립은 이 검사만 통과하면 진행한다. `lib/serverScreener.ts:19`는 그 결과를 메모리와 캐시에 넣고 새 시각을 제공한다. 실제 실패 원본으로 이 경로의 조립 통과를 재현했다.
3. **검사와 운영이 분리돼 있음.** `scripts/capture-snapshot.ts:135`는 회귀·요청 실패로 작업을 실패시키지만, 결과는 아카이브에만 남는다. 운영 캐시는 이 아카이브를 읽지 않고 다시 수집한다. 일일 검사가 실패해도 운영 공개를 막는 연결이 없다. 마지막 성공한 아카이브 기준선을 보존하는 것과 마지막 정상 운영 데이터를 보존하는 것을 구분하지 못했다.
4. **사용자가 장애를 판별하기 어려움.** 상단에는 새 `updatedAt`과 작은 ‘일부 자료 미수집’만 나오고, 표에는 ‘FDV 미확인’과 대시가 보인다. 상세에는 조회 실패 사유가 있지만 기본 표에서 원천 부재·조회 실패·정의 보류·이력 부족이 쉽게 구분되지 않는다. 장애 시작, 마지막 정상, 영향 종목 수가 없다.
5. **검증 범위를 과대해석함.** 기존 테스트는 매핑 누락·재시도·회귀 감지를 검사했다. 외부 API 전면 실패 후 공개본이 유지되는지, 장애 표시가 유지되는지, 서버 재시작·날짜 변경 후에도 마지막 정상본을 읽는지는 입증하지 못했다. ‘누락 0’은 배포 순간의 확인이었으며 지속 운영 보증처럼 전달해서는 안 됐다.
6. **시각과 이력이 부족함.** `updatedAt`은 수집 결과 조립 시각이다. 정상성 검증 시각이나 각 원천 자료의 기준 시각이 아니다. 공개본 식별자·공개 이력·장애의 최초/최종 관측 시각을 영구 기록하지 않는다. 이전에 측정한 78초 첫 접속 지연도 사용자 요청 중 수집을 실행하는 같은 구조와 연결된다.

현재 코드를 유지하면 제공처 403·429·타임아웃, 일부 응답 누락 등에서 유사 증상이 재발할 수 있다. 재시도 보완만으로는 이 구조를 고칠 수 없다.

## 재발 방지 실행 계획

‘외부 원천이 절대 실패하지 않음’은 보장할 수 없다. 완료 기준은 **실패를 원천 부재나 정상 최신 자료로 조용히 바꾸지 않고, 영향과 발생 구간을 추적하며, 실패 후보가 검증본을 덮어쓰지 않는 것**이다. 전체 프로젝트 목록은 유지한다.

| 순서 | 변경 내용 | 통과 조건 |
|---|---|---|
| 1. 공개 차단과 복구 | 수집 후보와 공개본을 분리한다. 공통 검증기가 필수 원천 요청 실패·형식 오류·설명되지 않은 값/구성원 감소를 검사한다. 실패 후보는 진단용으로 보존하고 마지막 검증본 식별자는 유지한다. 검증본이 없으면 명시적 준비/장애 상태를 보여준다. | 이번 실제 실패 원본을 넣어도 공개본 ID와 정상 시각이 바뀌지 않는다. 403 전체 실패와 한 배치 실패를 모두 검증한다. |
| 2. 단일 수집·공개 경로 | 사용자 접속에서 전수 수집을 제거한다. 독립 실행한 수집 결과를 검증·저장한 뒤 공개본 포인터를 원자적으로 바꾼다. 사이트·일일 검사·배포 검증이 같은 데이터 ID를 확인한다. 완료가 늦은 과거 작업이 최신본을 덮어쓰지 못하게 한다. | 원천을 차단해도 첫 접속은 보존 자료 또는 장애 화면을 즉시 반환한다. 캐시 삭제·서버 재시작·UTC 날짜 변경 후에도 같은 검증본이 유지된다. |
| 3. 공개·장애 이력 영구 보관 | 모든 수집 시도와 공개본에 ID, 코드 버전, 원천 URL/ID, HTTP 결과, 원천 및 수집 기준 시각, 해시, 영향 목록, 판정을 저장한다. `lastSuccessfulAt`, `lastAttemptAt`, `firstFailureObservedAt`, `lastFailureObservedAt`, `publishedAt`을 분리한다. | 임의의 공개본을 재현하고, ‘마지막 정상 관측~최초 실패 관측’ 및 최초 영향 공개본을 조회할 수 있다. 정상 시각은 실패 때 갱신되지 않는다. |
| 4. 화면과 운영 경보 | 상단에 사용 중인 검증본 시각·지연·장애 제공처·영향 프로젝트 수를 표시한다. 각 행/지표에 조회 실패, 원천 미제공, 토큰 연결 필요, 정의 검토, 이력 부족을 구분한다. 장애 발생·범위 확대·회복을 운영 이벤트로 남긴다. 예약 작업 지연도 감시한다. | Sat Rush FDV 공란의 원인과 마지막 정상 관측을 상세 진입 없이 알 수 있다. HTTP 200·금액 null과 실제 제공처 0을 혼동하지 않는다. 장기 장애가 작은 문구에 묻히지 않는다. |
| 5. 전수 검증 강화 | 원천 목록 전체, 정식 ID, 부모·하위 구성, 기간, 원본 집계 및 계산값을 대조한다. 단순 숫자 존재 검사와 금액 일치 검사를 나눈다. 원천 정의 변경·정상 종료·미보고 일자 등은 오류 유형을 분리해 검토 이력을 남긴다. | FWA·Sat Rush뿐 아니라 전체 대상의 누락/공란 사유가 집계된다. 원인 미확인 감소를 정상 기준선으로 자동 승격하지 않는다. 정상적인 원천 변경도 조용히 무시하지 않는다. |
| 6. 장애 주입 후 배포 검증 | 403·429·타임아웃·200 빈 배열·응답 형식 변경·부분 배치 실패·ID/정의 변경·UTC 전환·캐시 유실·동시 수집 순서 역전을 통합 검증한다. 테스트 원천으로 장애와 회복을 재현하고, 실제 운영에서는 공개 ID·상태·브라우저 표시를 읽어 확인한다. | 장애 중 기존 검증본 유지, 명시적 경고, 회복 후 한 번의 원자적 교체, 기록 보존을 함께 통과한다. 기존 `npm run deploy:production` 경로와 데이터 정확성 검증을 유지한다. |

### 설계 시 지킬 제약

- 오래된 검증본에는 실제 기준 시각과 지연을 표시한다. 어제 시세를 오늘 시세로 표시하거나 어제 시세·오늘 수익을 무표시로 섞어 배수를 만들지 않는다.
- ‘미제공/정의 검토/날짜 부족’은 모두 API 장애와 동일한 상태가 아니다. 정상적인 신규 프로젝트와 명시적 미제공은 사유를 보존한다. 개별 정의 검토 경보가 전체 제공처 장애 경보를 가리지 않게 한다.
- 0과 null은 그대로 구분한다. 양수→0도 제공처 변경과 원천 근거를 확인한다. 과거 가격이나 총발행량으로 현재 FDV를 임의 복원하지 않는다.
- 시세 대체 경로는 정식 자산 ID, 값의 정의와 기준 시각, 제공처 이용 조건을 검증한 경우에만 사용한다. Sat Rush 단일 하드코딩으로 끝내지 않는다. CoinGecko 접근 방식은 공식 오류 원인과 허용 경로를 확인한 후 정한다.
- 영속 저장 및 예약 실행은 현재 계정·비용 범위에서 가능한 방법부터 확인한다. 새 유료 서비스나 API 요금제를 이 계획에서 확정하지 않는다.
- GitHub의 예약 시간이 곧 실행 시간이라는 가정을 하지 않는다. 검증본 나이와 작업의 실제 시작/완료 시각으로 지연을 판단한다. 알림 채널은 구현 시 정하고, 이 진단에서는 외부 메시지를 보내거나 자동화를 등록하지 않았다.
- 데이터 상태를 사이트에서 즉시 읽을 수 있어야 한다. 수집 장애 감지 목표는 각 수집 시도 종료 시점이며, 공개 전 차단은 필수다. 별도 경보 전달 지연 목표와 수집 주기는 실제 실행 환경을 정한 뒤 수치로 고정한다.

## 신뢰 복구를 선언할 조건

1. 지금 보존한 장애 원본으로 공개 차단과 마지막 검증본 유지가 재현된다.
2. 종목 전체가 표시되며, 계산 불가 사유와 원천·기간·시각이 분리된다.
3. 처음 들어오는 사용자도 원천 수집 완료를 기다리지 않는다. 자료 준비 여부와 장애 상태는 즉시 보인다.
4. 배포 직후 검증에 더해 한 번 이상의 UTC 날짜 전환과 정기 수집을 관찰한다. 수집 장애→회복의 검증은 테스트 환경에서 의도적으로 수행한다.
5. 문제 발생 후 ‘언제부터, 어떤 공개본에서, 어떤 종목의 어떤 값이 달라졌는지’를 저장 기록으로 답할 수 있다.

현 시점은 이 조건을 충족하지 않는다. 이번에 확인한 것은 장애의 실재, 수집 실패의 공개 허용 경로, 영향 범위, 그리고 기록의 한계다.
