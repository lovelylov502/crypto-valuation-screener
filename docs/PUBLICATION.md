# Verified data publication

The September 29 incident exposed two independent paths: a daily checker could fail while a request-time collector still replaced the live data. The site now has no collection or publication capability. Its static shell loads immediately; the API reads one persisted, hash-checked, verified snapshot.

## Single writer and persistent storage

The existing public repository's GitHub Releases store data outside Git commits. Generated artifacts remain out of commits. `.github/workflows/daily-snapshot.yml` is the sole writer, including manual dispatch, with one concurrency group and cancellation disabled. Collection slots start at 02:00 and 14:00 UTC (11:00 and 23:00 KST), twice daily. GitHub primary and +30/+60-minute backup wakes share that writer with two independent daily Vercel cron calls. Both providers are best-effort; actual start records determine whether the 90-minute deadline was met.

Vercel `/api/cron/collect` authenticates `CRON_SECRET`, accepts only the configured cron during its original 90-minute window, and dispatches canonical `main` with a signed receipt. It never collects upstream data or publishes a release. Production-only `SCREENER_DISPATCH_TOKEN` is a dedicated fine-grained GitHub credential restricted to this repository with Actions write permission. The same random signing value is stored as Vercel `CRON_SECRET` and GitHub Actions `SCREENER_SCHEDULER_SECRET`. Secrets must never enter Git, evidence files, or logs. Preview deployments cannot dispatch. Configuration, authentication, and dispatch failures return non-success responses without substituting another credential or retrying an ambiguous dispatch.

Inside the writer lock, `due` verifies automatic receipts and the authoritative start journal before any collection. Native schedules, signed Vercel dispatches, and ordinary manual dispatches all skip a slot already started, including a failed attempt. Only an explicit first manual bootstrap with no existing journal is exempt. A queued Vercel request retains its original slot; after the next slot begins it is rejected, never relabeled. `trigger.json` and every completed or interrupted collection report retain the trigger source and planned slot; external receipts additionally retain requested time, the Vercel proxy request ID, and signature-verification result. Receipt signatures and secrets are not archived. The endpoint requires Vercel's cron user agent and schedule header before signing. For acceptance, cross-check the archived verified receipt, workflow inputs/code, configured Vercel cron, and the absence of an operator-triggered invocation; retain provider logs while available (Hobby retains only one hour). A provider log that has expired is not proof of non-execution. If automatic origin cannot be established, exclude the collection from the scheduled count. Manual executions and skipped jobs never count. See [acceptance and operation evidence](./RELIABILITY_ACCEPTANCE_2026-10-03.md).

The October 3 14:17 UTC slot had no run/start record after its 15:47 UTC deadline even though the workflow was active and its default-branch cron was correct. Each slot now has backup wakes at +30 and +60 minutes. Under the same workflow concurrency lock, a due guard reads the authenticated GitHub Release journal before tests, start persistence or source collection. A start at or after the current slot skips the entire collection, even if that attempt failed or is still marked running; the next slot may collect again. Missing/unreadable/invalid/future start evidence fails closed. Thus six daily workflow wakes normally produce two source collections. Manual dispatch retains its explicit behavior and is excluded from scheduled acceptance counts. Skipped wakes do not create journals or count as collections; their decision is retained in the workflow summary, and collection reports include `scheduledFor`. Late natural wakes may recover the current slot without resetting its original deadline. This mitigates an individual missing wake; it cannot guarantee execution during a GitHub scheduler outage.

Each run publishes a start journal **before** collection and a completion journal after validation. Each has a unique run/attempt tag, previous-journal link, snapshot pointer, real collection times, code commit, provider outcomes and incident state. Assets upload to a draft release, their SHA-256 digests must match, and only then is the complete release made public/latest. Old assets are never replaced or deleted. Failed uploads leave the previously visible journal intact. Before publication the writer rechecks its parent; it rejects superseded, duplicate or older attempts. Only the canonical main GitHub workflow can call the writer. Do not publish journals locally or create another writer outside that concurrency group.

Completion archives contain the scored candidate, raw joined inputs when available, independent source-universe witness, exact value/coverage changes against the published baseline and checksummed artifact inventory. Blocked candidates are retained for diagnosis, but their amounts never enter the public snapshot. The journal points to the previous verified snapshot until a newer candidate passes **all** checks. Its original date and amounts remain together; no old quote/new revenue mixing is allowed.

GitHub Actions artifacts are still retained for 60 days as an additional copy; the Release archives have no application expiration/deletion job. Administrative deletion or a GitHub outage remains possible: hash/read failures produce an explicit error and cannot trigger a fresh crawl. A warm instance retains its last verified snapshot. A cold instance reads the same persisted snapshot; when the archive itself is unreachable it returns a clear unavailable state rather than inventing data.

## Gate

`snapshotErrors` checks rule version, date, required source observations, full collection accounting, every provider lookup, empty quote responses, original Revenue visibility and every row's fundamental contract. `assessCandidate` adds original-date ordering, cross-midnight rejection and comparison against the actual published baseline: lost source membership, changed identities, quotes/positive values, original amounts, complete period coverage and definition review all block publication. Independent source witnesses additionally check the entire source universe and available-but-hidden Revenue amounts.

A legitimate upstream removal or definition/coverage change requires evidence. The collector separately verifies a latest-completed-UTC-day reporting delay against the independent per-protocol summary for the affected Revenue or HoldersRevenue metric: IDs, names, methodology and parent component sets must match; that exact latest date must be absent, the preceding date and every other required date must be explicit. Only the affected incomplete periods are accepted as unavailable, with original source amounts retained and ratios withheld. Empty/failed responses, older gaps, wider parent scopes and other loss types cannot use this route. The raw independent summaries and their hashes are archived as `pending-history-review.json.gz`.

Other reviewed upstream changes can be recorded in `lib/reviewedSourceChanges.json`. This is a dated source-verification rule, bound to the full original baseline hash, collection date and each affected field's identity, component/definition fingerprint and UTC window/count. A different baseline, day, scope or missing-day count invalidates the review. Applied entries are archived as `source-change-review.json` and the report separates reviewed from unreviewed changes. Every other loss still blocks publication; source failures and financial/collection contracts are never waived. No unreviewed exception list or automatic baseline reset exists. The September 30 review and its independent evidence are documented in [the recovery record](./INCIDENT_2026-09-30_RECOVERY.md).

Previously complete parent histories get an extra current-source recheck only when their exact prior window loses coverage. Matching IDs, child sets, methodology and overlapping values remain mandatory; the baseline supplies identities and window lengths, never old amounts. Source history recovery cannot renew an economic definition review or authorize a ratio.

`reviewUpstreamChanges` also verifies changes that recur after the original recovery date. The complete independently fetched universe must confirm project removals; its explicit IDs and fresh market-ID requests must confirm token identity changes or withdrawal. Missing quote fields are re-requested from both linked providers. An available value cannot be approved as absent. Previously linked CMC IDs omitted from discovery, and incomplete discovery records, are queried directly during collection using current responses only.

For incomplete Revenue/HoldersRevenue windows, each selected component's individual summary must match its ID, name, parent, methodology and double-counting status. The intersection of its explicit UTC dates must reproduce the candidate's exact reported-day count; missing provider totals must also be absent in those summaries. This supports older/multiple gaps and parents with wider unrelated children without inventing zero or including that wider scope. Definition changes remain unreviewed for financial calculation; the independent witness must reproduce the new fingerprint before publication can record that change. These proofs and raw responses are archived in `upstream-change-review.json.gz`. Source failures, malformed evidence, available-but-dropped values and unproven changes still block publication. No dated exception or baseline reset is required for these independently verified source states.

When a previously reviewed holder stream loses calculation eligibility after a definition change, the independent holder witness must reproduce every current component, its review state, and all original/eligible/excluded amounts. Every previously eligible component must now have a changed definition; no eligible component may remain in this all-withheld path. Only an absent calculated history with a null P/HR can be accepted as a definition hold. Input loss, missing components, changed raw amounts, inconsistent definitions, and request failures still block publication. The new definition is never automatically approved for calculation. See [the acceptance rubric](./RELIABILITY_ACCEPTANCE_2026-10-03.md).

If a previously available non-parent metric disappears from an overview but its project remains in the current directory, the collector rechecks the individual summary. Canonical source ID, name, explicit market IDs, parent/double-counting status and the existing reviewed methodology must match before current amounts enter the original aggregation. Removed projects and mismatched/changed definitions cannot use this recovery. A recovered Revenue row exposes its actual summary URL and observation time; no baseline amount is copied.

Initial recovery is allowed only once, through a checksum-pinned seed that contains a preserved snapshot, its independent source witness and a passing prior full audit including independent missing-quote checks. The bootstrap retains its historical collection timestamp. It cannot replace an existing journal and must be followed by a normal collection. Historical recovery is never a current-data success.

## Read and monitor

`/` is a static shell. `/api/screener` and `/api/status` read the same journal. The API verifies compressed snapshot hash, original timestamp and all snapshot contracts; cached objects survive ordinary reads and refresh from persistent storage after restart. A newer archive read failure retains the old **snapshot ID as well as its values**, with an explicit store error. No request handler imports `fetchCoins` or `buildScreener`.

The browser polls the small status endpoint every ten minutes while visible and fetches rows only when the published ID changes or query controls change. The status clock checks every 30 seconds. Source/gate failure produces `공개 보류`; an unfinished durable start after 15 minutes produces `수집 중단`; a publication that misses a scheduled slot plus a 90-minute grace period is delayed. If no new durable start exists by that deadline, the distinct label is `예약 실행 미확인`. Crossing a UTC date alone does not make the scheduled snapshot late. Errors persist during retries. The banner labels the exact historical data time, and details expose the tracking start, first/latest failure observation, last verified data date, recovery, affected project/field counts, complete change report and task record. Tracking start is disclosed; missing pre-migration history is not fabricated.

The collector holds a referenced ten-minute deadline while its asynchronous work runs, logs its stage, and saves a diagnostic report on timeout. Publication requires `comparisonCompleted=true`; missing results cannot be accepted because a process exited with code zero. An interrupted or incomplete comparison is displayed as unknown, never as zero changed projects. Legacy journals without the field are treated conservatively unless their published/unreviewed-loss result proves comparison ran.

## Deployment verification

Canonical root/repository/Vercel/clean-main guards and financial assertions stay mandatory. The static shell has no embedded snapshot, so the old duplicated HTML/API timestamp comparison applies only to legacy SSR output. New readback requires a consistent persisted snapshot ID across all API queries and an exact archive/date match.

The full-universe audit always verifies every public row against the hash-checked stored snapshot, validates every financial/collection contract and replays the archived independent source witness. Within 45 minutes of a published collection it additionally checks live upstream sources and missing quotes. Between collections, `verified-scheduled-snapshot` audits the archive and its original source witness, reports `liveSourcesChecked=false`, and still fails if the scheduled deadline was missed. It does not compare an intentionally retained snapshot to a later, changed source feed. For an explicitly blocked/running collector it verifies protected operation: the blocked report must name the identical retained baseline ID/hash, have actual errors and an incident, or a running job must be within its deadline. It records `mode=protected-last-verified` and `currentCollectionPassed=false`. This pass proves containment and availability of historical verified data; it is **not** a current source-coverage/recovery pass.

## Verification cases

Tests cover 403, 429, timeouts, empty responses, silent loss, malformed evidence, midnight rollover, restart/cache loss, interrupted jobs, overlapping/late completions, recovery, wrong hashes, partial uploads, changed publication parents and unavailable storage. The preserved September 29 incident must fail against the preserved September 28 verified baseline without changing its published ID/hash/date. Production verification additionally retains the actual GitHub run, publication and deployment IDs, browser state and cold-shell timings.
